# Слой данных Jira — спринт 2, Бэкенд А

База пакета: main c646d462531ae235ccff1558e086cef29b87d1f6 (включая PR №9). Только тестовый SCRUM, доска 1, один Jira-сайт. Владелец — assignee.accountId. При недоступности Jira остаются последние сохранённые разрешённые задачи; неуспешный запуск не продвигает курсор. API/отображение времени последнего успеха принадлежат Бэкенду Б.

## Поток

RestSource или RawFileSource → сырые данные → Policy.evaluate → normalize → RealStore → модели из main. Запрещённая задача с известным ID удаляется вместе с дочерними данными. Ошибка чтения/разбора — failed, не доказательство удаления. Отсутствие задачи в полном поиске в этом спринте не запускает удаление.

IssueDTO и models.py не изменены. RawSource — отдельный внутренний интерфейс со справочниками, raw_issues, raw_issue_detail и comments. Старый FileSource сохранён для DTO-тестов, но run_sync не принимает его: загрузка готового DTO не должна обходить политику. get_source теперь возвращает raw-источник. Это изменение внутреннего контракта следует обозначить в contract PR.

Policy возвращает Decision(jira_id, owner_ref, allowed) отдельно от DTO. В БД попадает только разрешённый DTO; RealStore записывает owner_ref в той же транзакции. Файлы selectors, views, serializers, identity, модели/миграции и профили ModuleUser этот пакет не изменяет.

## Установка

```powershell
python -m pip install -r requirements.txt
```

Зависимости входят в общий requirements.txt через отдельный PR с настройками. Для локальной синхронизации Django читает `.env` из корня репозитория. Если PostgreSQL запущен через `docker compose up -d db`, можно запускать Python на хосте с `DATABASE_URL`, указывающим на `127.0.0.1:5432`. Такой запуск читает Jira-настройки из того же локального `.env`.

Реальные секреты не входят ни в fixtures, ни в пакет. JIRA_BASE_URL остаётся адресом сайта для ссылки сотрудника; при scoped token API URL может отличаться. Scoped token с этим пакетом отдельно не проверялся. HTTP-клиент не использует .netrc и proxy из окружения: для требуемого корпоративного proxy потребуется явная конфигурация клиента.

Порядок priority_order берётся из JIRA_PRIORITY_IDS, а не из числового ID, локализованного имени или недокументированного порядка ответа API. Неизвестный ID получает null. Порядок статусов берётся из board configuration. Sprint/Rank определяются по схеме и конфигурации доски.

## Первичная настройка и запуск

1. Применить существующие миграции PostgreSQL. Новых миграций нет.
2. Выполнить первый full: он создаст справочник проекта выключенным, задачи не выдаст. Либо заранее создать JiraProject с id=10000, key=SCRUM.
3. Через существующую Django admin включить проект SCRUM. Создать включённое JiraVisibilityRule: project=SCRUM, source=label, expected_value — JSON-строка `"intern-visible"`, field_def пустое. Само присутствие настройки JIRA_VISIBILITY_LABEL в окружении не создаёт правило.
4. Выполнить full повторно. Для стандартного mock-набора из 12 задач разрешены 8. Остальные — без метки, без исполнителя или с отозванным разрешением.
5. Привязка ModuleUser.owner_ref к accountId — стык с Бэкендом Б. Слой А не изменяет профили; совпадение jira_user без owner_ref недостаточно.

```powershell
python manage.py sync_jira --full --dry-run
python manage.py sync_jira --full
python manage.py sync_jira --incremental
python manage.py sync_jira --incremental --since 2026-11-17T00:00:00Z
```

dry-run читает правила из БД, но не создаёт задачи, справочники или JiraSyncRun. Это отличие от режима первого спринта «без БД вообще». Без настроенного разрешающего правила успешный dry-run покажет запрещённые задачи — это ожидаемо.

Запись требует PostgreSQL. На SQLite проверяются данные/транзакции через явную тестовую подмену lock; рабочая команда не отключает блокировку молча. Session advisory lock используется на том же соединении Django; подключать через PgBouncer в transaction pooling нельзя. При завершении процесса сервер освобождает session lock. Следующий владелец lock помечает оставшиеся running-запуски как failed/interrupted.

## Incremental и изменения правил

Первый запуск источника — full. Далее курсор берётся из started_at последнего успешного запуска этого источника с перекрытием; failed и запуск другого источника не продвигают его. Пользовательский --since может расширить окно, но не отодвинуть его за последний успех. Для JQL учитывается timeZone технического пользователя из /myself, дата округляется вниз до минуты.

После списка изменившихся задач отдельно перечитываются сохранённые задачи, которые в список не попали. Это применяет отзыв метки/владельца и локальные ограничения; для небольшого MVP приемлемы дополнительные запросы. Новые разрешённые старые задачи после расширения политики требуют full. При смене сайта, манифеста или настроек политики выполнить full до следующего incremental. Для mock и rest использовать отдельные тестовые БД: одинаковые Jira ID в raw fixtures не означают одинаковых пользователей.

При изменении правил доступа безопасный порядок: закрыть проект, изменить правила, выполнить full, затем включить проект и повторить full. При выключении проекта/всех правил удаляются его старые задачи; при выключении текстов удаляются старые описания и комментарии, даже если последующий запрос Jira не удался. Это применение локального запрета; обычная недоступность Jira при неизменной политике не удаляет сохранённые задачи.

Динамическая смена области/сайта не поддерживается. Текущее JiraSyncRun не хранит fingerprint подключения/политики; автоматическое обнаружение смены подключения требует отдельного согласования схемы. Демо первого спринта не использовать как baseline для incremental raw: начать с full.

## Нормализация и политика

- Поиск охватывает проект без фильтра intern-visible. Для неизвестных или неполных данных запуск не считается успешным.
- Статусы: new → todo, indeterminate → in_progress, done → done.
- Исполнитель идентифицируется по accountId; email не переносится. Пустой исполнитель не получает владельца.
- Спринт выбирается по свежему справочнику: active, иначе ближайший future; без даты — после датированных, при равенстве — по ID. Несколько активных спринтов отклоняются как неподдерживаемый MVP.
- Описания/комментарии выключены. При включении требуется rendered HTML, который очищает nh3. ADF не преобразуется в HTML строковым приведением.
- Комментарии читаются полностью, ограниченные visibility и jsdPublic=false исключаются. Частичный список не заменяет сохранённый.
- Только включённые display-поля попадают в custom_fields. Поддерживаются string/number/boolean. owner/policy_flag/intern_description не попадают в публичные поля. Сложные типы и intern_description — следующий спринт.
- Правило custom_field поддерживает точное сравнение JSON-значения с учётом типа, только для включённого поля purpose=policy_flag. Несуществующее/выключенное поле не разрешает доступ. Отсутствующий запрошенный ключ — ошибка, явное несовпадение — запрет.
- Служебные owner-метки intern:* и разрешающие метки удаляются из DTO labels. Вложения не запрашиваются.
- HTML-очистка не удаляет персональные сведения из текста. За тестовый «паспорт» отвечает запрет description, а не регулярное выражение.

## Сбои и журнал

429/5xx и транспортные сбои повторяются ограниченно; 401/403/404 и redirects не повторяются. Retry-After соблюдается как минимальная задержка; если он превышает лимит ожидания, запуск завершается ошибкой, а не повторяет запрос раньше. HTTP тела и заголовки авторизации не входят в журнал. По задаче фиксируются стадия и класс исключения; не более 20 текстов ошибок, общий счётчик не ограничен.

Ошибка одной задачи позволяет обработать остальные, но весь JiraSyncRun получает failed. Каждая задача со связанными объектами атомарна. Никакой массовой очистки по отсутствию в failed/full нет. Если Jira скрыла или удалила задачу и возвращает 404, этот спринт сохраняет прежнюю запись до согласованной полной сверки; это ограничение хранения последнего набора, а не доказанный актуальный доступ Jira.

## Проверки и предел готовности

В пакете есть тесты HTTP, raw/DTO, нормализатора, политики, транзакций, курса incremental, CLI и PostgreSQL lock. Тесты слоя А очищают настройки реальной Jira из окружения и не ходят на сайт разработчика.

```powershell
python -m pytest -q
python -m ruff check .
python manage.py check
python manage.py makemigrations --check --dry-run
```

На SQLite тест advisory lock пропускается. Для приёмки его обязательно выполнить на PostgreSQL, затем проверить live rest на тестовом сайте, повтор загрузки и отзыв разрешения. Библиотечные HTTP-тесты не являются живой проверкой Jira. --loop, ночная сверка по отсутствию и webhook в этот пакет не входят.

## Стык с Бэкендом Б

Только описание ожиданий: профилю нужен тот же непустой accountId в owner_ref; API читает локальные данные и безопасные поля журнала; время актуальности — последний успешный запуск нужного источника. Показ старых данных при сбое принят для тестового MVP. Поля policy/owner не сериализуются; связи выдаются только при доступе к цели. Реализацию этих пунктов выполняет Бэкенд Б.

## Уточнения аудита 18 ноября

Подтверждённая смена исполнителя закрывает прежний owner_ref до чтения комментариев и нормализации. Если последующий разбор или запись упадут, старая запись остаётся с owner_ref=null и не выдаётся ни прежнему, ни новому владельцу. Успешный повтор присваивает нового владельца в транзакции записи. При неизменном владельце ошибка обновления сохраняет прежние данные. Dry-run не закрывает доступ и не пишет в БД.

Подтверждённый запрет по правилам не требует дальнейшего чтения assignee: отсутствие этого постороннего поля не должно препятствовать отзыву разрешения. Недостающие данные, необходимые самому правилу, по-прежнему считаются ошибкой, а не доказанным запретом.
