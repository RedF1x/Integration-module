# Фоновая загрузка Jira

Воркер Procrastinate читает проект SCRUM доски 1 через REST или из mock-манифеста. Каждое задание обрабатывает одну страницу поиска или одну пачку сверки. Задачи сохраняются в существующих таблицах Django после проверки видимости. При работе с живой Jira используйте отдельную PostgreSQL-базу и токен с правом чтения.

## Запуск

Compose получает параметры из локального `.env`. На чистом развёртывании заполните его по `.env.example`. Для живого источника задайте `JIRA_SOURCE=rest`, адрес сайта или разрешённого API, email и токен технической учётки. На тестовых данных используйте `JIRA_SOURCE=mock`. В одном развёртывании используйте один источник для записи. В существующей базе проверьте включённые проект и правила видимости: новый проект по умолчанию выключен.

```powershell
docker compose up --build -d
docker compose ps -a
docker compose logs --tail 40 worker
```

Сервис migrate применяет миграции. Затем стартуют web и один worker. Первый сигнал планировщика приходит на границе минуты. При работе без Compose примените миграции к PostgreSQL и запустите отдельный процесс из каталога проекта:

```powershell
python manage.py migrate
python manage.py procrastinate worker --queues jira --concurrency 1 --delete-jobs successful
```

## Интервалы и восстановление

* `JIRA_SYNC_INTERVAL_SEC` — интервал поиска изменений в секундах, по умолчанию 60. В JQL время округляется до минут. Перекрытие запросов задаёт `JIRA_OVERLAP_SECONDS`, по умолчанию 300.
* `JIRA_RECONCILE_INTERVAL_SEC` — интервал полного обхода и сверки, по умолчанию 3600 секунд. Если сохранённый ID отсутствует в завершённом полном поиске, воркер перепроверяет его. Сетевая ошибка не подтверждает исчезновение.
* Следующая страница ставится сразу. В БД хранятся маркер страницы и граница последнего успешного прохода. После перезапуска периодический сигнал подбирает незавершённый проход. Истёкший маркер вызывает повторное чтение окна. Одинаковые ID обновляются на месте.
* При ошибке предыдущие успешные данные доступны до подтверждённого отзыва. Пока Jira недоступна, фактическая задержка обновления может превышать заданный интервал.

Если ответ пачки уже подтвердил отзыв, воркер сразу закрывает доступ к этой задаче. Отсутствующий в пачке ID проверяется отдельно. При сетевом сбое или HTTP 429 воркер сохраняет место и планирует повтор. Справочники проекта кэшируются на 15 минут, список спринтов обновляется при новом проходе.

Если в задаче испорчены метки или данные исполнителя, воркер удаляет её локальную копию. При ошибке отображаемого поля он оставляет прежнюю копию для того же владельца и обрабатывает остальные задачи. Проход завершается со статусом `failed` и списком числовых ID в журнале. Следующий проход повторяет окно от последней успешной загрузки.

Между страницами ручная команда `sync_jira --full` сообщает, что фоновый проход занят. В режиме `--dry-run` команда доступна для диагностики.

Посмотреть результаты и состояние очередного прохода:

```powershell
python manage.py shell -c "from jira_integration.models import JiraSyncRun; print(list(JiraSyncRun.objects.order_by('-pk').values('mode','status','created_count','updated_count','deleted_count','failed_count')[:5]))"
python manage.py shell -c "from jira_integration.queueing.models import SyncCursor; print(list(SyncCursor.objects.values('source','phase','watermark','last_full','next_due')))"
```

В Compose перед каждой командой Python добавьте `docker compose exec web`. Для работы очереди требуется PostgreSQL. SQLite подходит для автономных тестов логики страниц и видимости.
